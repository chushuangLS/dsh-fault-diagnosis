一、项目概述

1.1 真实需求来源

本作品的需求直接来自作者本人的日常运维工作，而非虚构场景：

  • 负责 23 间机房教室、约 1840 台计算机设备 的日常维护
  • 管理一支 50 人的学生运维团队
  • 每周值班 3–4 次，组织每周两次机房大扫除

1.2 要解决的问题

在高频运维工作中，暴露出三个具体痛点：

痛点 具体表现
高频故障重复出现 无法开机、网络中断、外设失灵等问题反复发生，每次都从头排查
排查依赖个人经验 新人上手慢，同一个故障不同人处理方式不一致，处理标准不统一
经验无法沉淀 老管理员毕业后经验随之流失，后来者仍需重新摸索
为什么这些痛点值得解决： 机房运维的核心矛盾是「故障种类有限但处理经验分散在人脑里」。 1840 台设备的故障模式其实高度重复，若能沉淀成可检索的工具， 就能把「依赖个人」变成「依赖系统」。

1.3 作品定位

本作品把机房运维经验沉淀成可检索、可复用的诊断工具，降低对个人经验的依赖。 与常见的「设备管理系统」不同，本作品的切入点是故障排查过程本身：

维度本作品的做法
输入方式 自然语言描述故障，不需要记忆关键词或分类编号
交互形式 对话式逐层追问，一次只问一个问题，模拟老师傅带徒弟的过程
知识来源 本校机房真实案例库 + AI 通用知识，并通过检索增强（RAG）注入
闭环设计 诊断结论自动写入报修台账，形成「排查 → 记录 → 统计 → 报表」闭环

2.3 数据存储设计

本项目不使用数据库，全部采用文件存储。这是刻意的选择：

为什么不用数据库： 本工具部署在机房现场的单机上，数据量极小（几十条记录 / 几个文件）， 引入 SQLite 或 MySQL 会增加部署复杂度，却带不来实际收益。 更重要的是——纯文件便于人工查看与直接编辑， 故障现场往往需要管理员直接用记事本打开台账确认， 这是数据库做不到的。
文件 是否提交 用途
data/fault_cases.json ✅ 提交 手工整理的知识库（23 条案例）
data/fault_cases_auto.json ❌ 忽略 程序自动沉淀的案例（运行时数据）
data/repair_records.csv ❌ 忽略 报修台账（含真实教室号，不公开）
data/classrooms.json ❌ 忽略 教室与设备台账
data/daily_tasks.json ❌ 忽略 日常报备待办
知识库分两个文件的设计理由： 手工整理的经验应当随仓库传递、可评审、可回滚； 而程序自动生成的数据属于运行时产物，不应污染提交记录。 两者分离后，程序只写 _auto 文件，永不覆盖手工知识库。

三、核心技术实现

3.1 对话式逐层排查

传统做法是用户输入故障后，一次性输出「5 个可能原因 + 5 个大步骤」， 内容长达上千字。在故障现场，管理员根本看不完，也无法根据实际情况推进。

本作品改为对话式逐层追问：

[用户] 501 教室电脑打不开
[AI]   按开机键后，机箱指示灯亮吗？风扇转吗？

[用户] 按电源没反应，灯不亮
[AI]   检查一下机箱后面的电源线两头有没有插紧，插紧后再按开机键，有反应吗？

[用户] 换了电源线还是不行
[AI]   看一下机箱背面电源上的开关是不是被关到"O"那边了，拨到"I"再开机试试？

[用户] 开关是开的，灯也不亮
[AI]   把电脑插到旁边正常的机位上试试，能开机吗？

[用户] 换了机位就能开
[AI]   这间教室有几台是这个情况？

[用户] 有 3 台
[AI]   【诊断结束】
       原因：这几个机位的插座没电（供电故障），主机本身没问题。
       数量：3 台
       处理：先确认是不是这几路插座对应的空气开关跳闸了……
       【需要报修】

关键实现——维护完整对话历史，让 AI 记住排查过程：

class DiagnosisSession:
    def __init__(self):
        self.history = []          # 对话历史
        self.classroom = ''        # 教室号
        self.quantity = 1          # 损坏数量
        self.need_repair = False   # 是否需报修
        self.self_fix = False      # 是否可自修

    def send(self, user_input):
        self.history.append({"role": "user", "content": user_input})
        response = self.client.chat.completions.create(
            model=MODEL,
            messages=self.history,      # 带上完整历史
            temperature=0.3,
            max_tokens=300,             # 限制长度，强制精简
        )
        reply = response.choices[0].message.content.strip()
        self.history.append({"role": "assistant", "content": reply})
        return clean_markers(reply), self.finished, self.need_repair

3.2 轻量 RAG 知识库

早期做法：把 fault_cases.json 全部案例塞进 system 消息。 案例一多就浪费 token，无关案例还会干扰判断。

现在的做法：先用本地关键词加权检索找出最相关的 Top-3 案例，只注入这几条。

检索算法

权重命中位置
×3.0故障分类一致
×2.0现象描述命中
×0.5可能原因命中（权重压低，见下）
额外加成命中关键特征词表（如"蓝屏""断网"给 3.0）
为什么「原因」权重只有 0.5： 原因是排查要点，用词宽泛（如"交换机断电或故障"里的"断电"）， 容易与无关领域偶然重合。曾经出现过查「电脑自动关机」时， 因共享「断电」一词而误命中网络类案例的假阳性。 压低权重并增加相关性判断后解决。

同义词归一

用户说「整间教室断网」，知识库里写的是「无法上网」—— 两边指的是同一件事，但字面完全没有重合，检索得分是 0。 

SYNONYMS = {
    '上网': ['断网', '上不了网', '无法上网', '不能上网', '连不上网'],
    '开机': ['开不了机', '打不开', '无法开机', '点不亮'],
    '黑屏': ['无显示', '没显示', '屏幕黑', '不显示', '没画面'],
    # ... 共 17 组
}

# 反向索引：说法 → 标准词（模块加载时构建一次）
_SYNONYM_LOOKUP = {}
for _std, _variants in SYNONYMS.items():
    _SYNONYM_LOOKUP[_std] = _std
    for _v in _variants:
        _SYNONYM_LOOKUP[_v] = _std

关键在于必须在切分之前扫描原文：用户说「教室上不了网」， 按标点切分只会得到 教室上、室上不 这类碎片， 上不了网 根本不会被提取出来。

粒度一致性

另一个被实际使用暴露的问题：查询「空调漏水」（4 字短句）整段保留， 而案例症状是长句、被切成 3-gram（空调漏、调漏水）—— 两边粒度不一致，交集为空，导致刚沉淀的新案例用关键词反而搜不到。

修复：长短句统一产出 3-gram，匹配时放宽为互为子串即算命中。

3.3 知识库自动沉淀

诊断结束后，若结论为「自己修」（已报修的不沉淀，因为结论尚未验证）， 系统把现象与结论提取成结构化案例写回知识库，实现越用越聪明。

为什么整段都要持锁（而不是只锁最后一步）： 最初的实现只给「追加」那一步加锁，查重和编号生成都在锁外。 并发沉淀时两个线程会读到相同的文件内容， 于是各自判断「没有重复」、各自算出同一个编号 —— 实测两条「外设故障」都拿到了 DEV-001。

编号是基于「当前全部案例」算出来的，只要这次读取发生在锁外， 拿到的就必然是过期快照，冲突只是时间问题。

3.4 设备状态四态模型

设备的可用状态设计为四种（面向运维）与两种（面向领导报表）两套口径：

系统状态 含义 报表归类
未报修 硬件故障，需要报修 损坏
可自修 非硬件问题，可自行修复 损坏
已报修 已联系维修，等待处理 损坏
已解决 已完结 正常
「损坏」的含义要有意说清： 它指的是设备能不能用，与报没报修无关。 因此 损坏 = 未报修 + 可自修 + 已报修。

界面上最初把这一项标成了「需报修」，但已报修的那几台并不需要再报修， 名称与实际含义不符，后来统一改为「损坏」。 这个概念区分很重要：「坏没坏」是设备属性，「报没报修」是处理进度， 两者是不同的维度，混在一个标签里就会说不清。
为什么报表要合并成两种： 这份报表是给领导看的，领导不关心修没修、谁去修， 只关心「现在有多少台能用」。因此报表口径为： 正常 + 损坏 = 设备总数，账目能直接对上。

「不能用台数」的统计口径

一条报修记录可以代表多台设备（如「第三排 5 台都开不了机」）， 因此统计台数时按数量字段累加，而不是数记录条数。 

def count_machines(records, statuses=None):
    """统计一批记录代表的机器台数（累加数量字段）"""
    total = 0
    for r in records:
        if statuses is not None and r.get('状态') not in statuses:
            continue
        total += get_quantity(r)
    return total

故障对象：电脑 / 教室设施

上面那个函数只解决了「一条记录代表几台」。但在真实运维里还有另一种情况： 坏的不是电脑。

总闸跳闸、交换机瘫痪、投影坏掉、教室断网 —— 这些是教室级设施。 它们会让整间教室不能用，可电脑本身一台都没坏。

如果没有这个区分，一条「总闸跳闸」只能记成「损坏 80 台电脑」： 既歪曲了设备状态，也让「损坏台数」这个指标失去意义。

故障对象 含义 统计口径
电脑 个别机器坏了 数量字段累加 → 计入损坏台数
教室设施 总闸、交换机、投影、空调、教室网络坏了 不计入台数，单独标记「设施故障」
只在两类之间划分，不再细分。 分太细会让登记表单变复杂，而运维人员真正要回答的只有两个问题： 「坏了几台电脑」和「教室能不能用」。

界面上这两个数字同时呈现： 教室 106 会显示「总数 76 / 正常 76 / 损坏 0」外加一个「设施故障 1」标记 —— 电脑都好的，但教室今天上不了课。

3.5 并发写入保护

Flask 默认多线程，多个请求可能同时「读-改-写」同一个数据文件。 没有锁时，后写的会覆盖先写的，导致数据丢失。

两层锁的设计

最终的实现用了两层锁，这是被两个真实缺陷逼出来的结构： 

@contextlib.contextmanager
def file_lock(target_path):
    """第一层：进程内可重入锁 第二层：跨进程文件锁"""
    key = os.path.abspath(target_path)
    with _get_local_lock(target_path):
        if key in _held_paths():      # 内层重入：不碰系统锁
            yield
            return

        fh = open(target_path + '.lock', 'w')
        try:
            import fcntl                  # Linux / macOS
            fcntl.flock(fh.fileno(), fcntl.LOCK_EX)
        except ImportError:
            import msvcrt                 # Windows
            msvcrt.locking(fh.fileno(), msvcrt.LK_LOCK, 1)

        _held_paths().add(key)
        yield
        # ……释放锁并清理

关键点一：必须加锁之后再读取

# 正确做法
with file_lock(AUTO_FILE):
    data = _load_auto()          # 先加锁，再读取
    data['cases'].append(case)
    _write_auto(data)

如果先读再加锁，读到的仍是过期内容，锁就白加了。

关键点二：「检查-写入」必须整体持锁

这是开发后期才暴露的一个缺陷。原来「文件不存在则创建」是这么写的： 

def init_file():
    if not os.path.exists(RECORD_FILE):          # ← 检查
        with open(RECORD_FILE, 'w', ...) as f:   # ← 'w' 是截断写
            csv.writer(f).writerow(FIELDS)

多线程同时首次调用时，都会通过 exists() 检查—— 因为此刻文件确实还不存在。随后后到的那个以 'w' 模式打开， 把先到者刚写入的内容全部清空。

这个缺陷只在 Linux 上暴露，而且时好时坏。 Windows 下 msvcrt 加锁与线程调度更慢， 恰好错开了竞态窗口，因此本地测试一直通过， 直到 CI 在 Ubuntu 上跑才暴露出来。

实测复现：60 轮并发首次创建，47 轮丢数据。 修复后同样的压测 0 轮失败。

修复方式有两处：一是让 init_file 全程持锁， 创建时改用 'x' 模式做二次保护（并发进入者会拿到 FileExistsError 而不是把文件截断）； 二是让 file_lock 支持重入。

关键点三：锁必须可重入

第二条修复有一个前提——如果锁不可重入，给 init_file 加锁会立刻造成死锁： 

update_status()
  └─ 持有锁
      └─ load_records()
          └─ init_file()
              └─ 又要加锁   ← 锁不可重入则死锁

业务代码里这种「持锁后调用另一个也会加锁的函数」的写法是合理且常见的， 因此锁在这一层做成可重入：同一线程重复进入时只累加计数， 只有最外层才真正去拿系统锁。

不能直接依赖 flock 的重入行为——同一进程内对同一文件 用两个不同 fd 加锁，各平台表现并不一致。所以重入由 Python 层 自己的 RLock 负责，系统锁只在最外层拿一次。

附带收益：修复后测试耗时从约 32 秒降到约 6 秒。 说明此前线程在锁上存在大量无谓等待。

验证方式：50 轮 × 12 线程高并发压测，0 轮失败； 另有两项防死锁测试（4 层嵌套加锁、锁内调用 load_records）， 均已固化进 tests/test_concurrency.py。

3.6 课表：从教务表格到「哪间空着」

教室坏了，最急的不是「这台怎么修」，而是这节课去哪上。 要回答这个问题，系统必须先知道：现在第几周、第几节，哪间教室有课。

解析教务导出的课表

学校导出的是一间教室一个 .xls 文件，格式固定： 

第 0 行   2026-2027学年第1学期 | 第一实验楼机房C104场地课表 | 座位数：80
第 1 行   节次 | (空) | 星期一 … 星期日
第 2-13 行  上午(一~四) / 下午(五~八) / 晚上(九~十二)
第 14 行  注--内容顺序为：课程<>周次<>教师<>教学班<>选课人数
          本学期2026-09-07正式上课至2027-01-24结束，共20周.

每个格子里是：

专业软件CAD/SU/(5-5节)1-8周/石嘉伟/专业软件CAD/SU-0002/选课人数：26

课程名和教学班名里都可能带斜杠，按 / 硬切会碎成 7 段。 所以解析时用「(N-N节)X-Y周」这一段当锚点，前后分别处理。 一个格子里还可能有两门课（不同周次交替），用换行分隔，都要提取。

文件格式按文件头判断，不看后缀——学校系统的后缀经常不准： OLE2 走 xlrd，ZIP 走 openpyxl。

作息时间：课表里没有的东西

课表只有「第几节」，没有几点到几点。而「现在有没有课」需要真实时间。 所以系统里存了一份全校统一的作息表，并提供一个快速生成入口： 填三个段的起始时间 + 单节时长 + 课间，就能生成 12 节，之后可逐节微调。

空余查询必须区分三类教室

类别含义
空闲已导入课表，且这一节确实没有排课
占用中这一节有课，附课程 / 教师 / 人数
未导入课表不知道有没有课
第三类绝对不能算成空闲。 不知道有没有课就说「空着」，会把学生引到正在上课的教室去。 这是这一块最容易被写错的地方，测试里专门锁了这条。

教师姓名在出口处脱敏

作品中不得出现真实教师姓名。脱敏放在后端返回时做，而不是前端—— 前端做的话，真名仍然出现在接口返回的 JSON 里，打开开发者工具就能看到。 复姓（欧阳、司马等）按两个字处理，避免变成「欧老师」。

3.7 运行总览：判定「能不能上课」

看板最容易做成「记了多少条」的统计表，但运维真正要回答的是一个问题：

这间教室现在还能不能上课？

「坏了几台」不足以回答它 —— 78 人的课坏 2 台照样能上； 教师机坏了却一台不缺也上不了。所以判定分三条，命中任一即算受影响：

条件判定依据
整间跳闸有未解决的教室设施故障，且现象含 总闸 / 跳闸 / 停电 / 短路 / 漏电
整间断网故障对象是教室设施，且提到 交换机 / 上联 / 路由器（机房课基本都要联网）
教师机故障未解决故障出现在教师机 / 讲台
教学设备故障故障对象是教室设施，且现象含 投影 / 幕布 / 音响 / 中控
座位不够可用台数 < 该节次选课人数（仅在这一节有课时判断）
「整间断网」这条是被真实使用逼出来的。 原先只判跳闸和教师机，于是「409 教室交换机坏了，明天 8 点有 74 人的课」 在系统里显示为「不影响」。可机房课离了网络就上不了。

预警要往后看，不能只扫今天

最早的实现只遍历「今天」的课。结果周日晚上打开系统时，今天没课 → 整块空白，而明天一早八点的课此刻就受着故障影响，完全看不到。 现在的范围是今天 + 明天，每条预警标清「今天 周六」「明天 周一」， 并且每一天的周次单独计算（周日跨周时会变）。

反复故障：同一处反复坏，指向的是根因

同一间教室、同一类故障累计 ≥3 次时单独列出。 反复换内存条可能是插槽氧化，反复报电源故障可能是教室供电不稳 —— 这类信息在逐条记录里看不出来，必须聚合。

分类口径上有一个坑：一开始把「故障现象 + 诊断结论」一起做关键词匹配， 结果结论里的鉴别诊断（「换线后显示器正常，问题在主机端」） 把「电脑打不开」判成了显示故障，18 条记录错了 3 条。 改成只按故障现象判——现象是运维人员自己的简短描述，稳定且没有干扰。

3.8 桌面化：把同一个应用装进窗口

Web 形态每次要先起服务、再开浏览器，还留一个控制台窗口。 演示和日常值班都别扭。目标只是换一种启动方式，不是重写： 用 pywebview 起一个内嵌 WebView2 的原生窗口，页面代码一行没改。

但"打个包"这一步，暴露出三个原本不存在的问题。

问题一：数据不能打进 exe

所有模块原先都写 os.path.join(dirname(__file__), '..', 'data')。 打包后 __file__ 指向临时解包目录，数据写进去，程序一退就清空。

所以把"代码在哪"和"数据写哪"拆开：

函数含义
res_dir()只读资源（模板、静态文件）。打包后在 sys._MEIPASS，程序退出自动清理，正好
data_dir()可写数据。优先级：环境变量 DSH_DATA_DIR → exe 同目录的 data/ → %APPDATA%（装在 Program Files 等只读位置时兜底）

首次运行时把知识库、决策树、空台账骨架铺到数据目录， 只补缺失的文件，绝不覆盖已有数据。

问题二：单文件 exe 根本起不来

[PYI-2580:ERROR] Could not create temporary directory!

单文件形态每次运行都要把自己解压到临时目录再启动， 这一步被杀毒软件拦了——换一个临时目录也一样。 所以改成文件夹版（onedir）：没有解包步骤，启动更快，误报也更少。 代价是交付时要整个文件夹一起拷走。

问题三：窗口偶尔起不来，而且说不清为什么

RuntimeError: Failed to resolve Python.Runtime.Loader.Initialize
             from ...\pythonnet\runtime\Python.Runtime.dll

pywebview 在 Windows 上要经 pythonnet 加载 .NET 组件。 实测同一份程序在 A 目录能开、B 目录报错； 排除了中文路径、工作目录、临时目录，原因仍未查清。

用户看到的现象会是"双击没反应"——比没有功能更糟。 所以加了一层兜底：pywebview 失败就用 Edge 的 --app 模式 开一个同样没有地址栏和标签页的窗口。 兜底里有个坑：Edge 已在运行时，新进程会把窗口交接给已有实例然后立刻退出， 靠 proc.wait() 判断"窗口何时关闭"就会误判—— 必须给 --user-data-dir 一个独立目录强制新实例。

API Key：为什么需要三处来源

打包给别人用，对方电脑上没有环境变量，一用诊断就报"未配置"。 读取顺序最终定为：

来源为什么需要它
进程环境变量服务器部署、临时换 Key 时不落盘
data/config.json桌面版首次启动弹窗填进去的
Windows 用户环境变量实测逼出来的：用户设过 Key， 但 pythonw 启动的进程里读不到，只能直接读注册表兜底

另外，"清除 Key"不能只是删掉配置文件里的那一行—— 后面还有注册表兜底会把它找回来，用户点了清除发现还能用，会以为坏了。 现在清除会写一个显式的 disabled 标记，短路掉所有来源。

安全边界

写 Key、打开目录、导出文件这类接口只接受来自 127.0.0.1 的请求。 默认的桌面版和 Web 版都只监听回环地址，本来就出不去； 但万一有人把 host 改成 0.0.0.0 开到局域网， 没有这道检查，同网段任何人都能改你的 Key。 不依赖"反正外面连不到"，而是显式判断。

3.9 界面性能：两个被「看着还行」掩盖的问题

两个性能问题都不是"代码写得慢"，而是用错了渲染路径。 它们的共同点是：功能完全正常，只是慢。

问题一：动画背景 + 满屏 backdrop-filter

全站有 16 种元素用了背景模糊，共 35 处，其中包括 每一条报修记录、课表表头的 12 个格子、5 个 KPI 卡。 背景静态时完全看不出来——一旦背景动起来， 这些区域每一帧都要重新做一遍高斯模糊。

改成半透明纯色背景（不透明度从 0.72 提到 0.92）后， 肉眼几乎看不出区别，但这几十次每帧模糊全部消失。

问题二：画布不是画得慢，是合成慢

剩下的背景动画仍然卡。这次先测量再改，在打包后的窗口里插临时帧率表：

条件整页帧率背景每帧绘制耗时
背景限 20fps145–182 fps—
背景提到 60fps46–55 fps1.0 ms
绘制只要 1ms，帧率却掉了三分之二 —— 说明瓶颈不在绘制。 DPR=2 时这块全屏画布是 3414×2134（730 万像素）， 每秒要把这么大一层重新合成 60 次，把合成资源吃满了。

把画布固定为 1 倍分辨率（1707×1067，面积只剩 1/4），帧率恢复， 线条是柔和的渐隐色，肉眼几乎看不出差别。

这里有一课：为了省 CPU 把帧率限到 20fps，其实是拿"背景一卡一卡"换了流畅。 在高刷屏上，20fps 的动画和 180fps 的界面放在一起， 用户的感受就是"掉帧"。优化要看用户看到什么，不是看指标降了多少。

四、意图控制策略

4.1 系统提示词设计

系统提示词是本项目最核心的设计。它的目标不是「让 AI 更聪明」， 而是约束 AI 的行为边界——把通用大模型改造成一个守规矩的运维助手。 

你是一名高校机房的运维工程师，正在通过对话帮学生管理员排查设备故障。

## 核心规则（必须严格遵守）

1. 每次回复只做一件事：要么问一个问题，要么给出结论。
   绝不一次列出多个问题或多个步骤。

2. 教室号已知时绝不再问。只有完全不知道教室时才问。

3. 第一步问清具体表现。如果用户描述很模糊（如"电脑打不开"），
   先问清楚具体现象，不要跳到排查。

4. 提问要多样化，禁止套模板。
   不要每次都问"指示灯亮吗？风扇转吗？"
   根据故障类型选择不同的切入角度。

5. 根据回答推进：用户说"不行"就排除这个原因，进入下一个全新的可能。
   绝不重复问同一个问题。

6. 用户答非所问时：先简短确认他的信息，再把原来的问题换个更简单的说法。

7. 确定原因后先判断故障范围，再决定要不要问数量：
   · 个别机器故障 → 先问「这间教室有几台是这个情况？」
   · 范围性故障（整间断电、整间断网、总闸跳闸）→ 不要问「几台」，
     整间都不能用了，问"几台电脑"没有意义

8. 数量要记住，不要写错。绝不能写 0 台。

9. 涉及电气安全时，第一件事是止损，不是继续排查：
   总闸 / 空气开关跳闸，只允许让用户推一次。
   · 推一次就恢复 → 可以继续按普通故障处理
   · 推上去立刻又跳、或根本推不上去 → 立即停止，
     明确告诉用户「不要再反复推闸」，直接给结论并报修
   出现焦糊味、冒烟、火花、发烫、漏电迹象时同样立即停止。
   绝不能让学生反复合闸、拆配电箱、动墙内线路。

## 结论格式

【诊断结束】
原因：<一句话说明故障原因>
数量：
处理：<自己修 / 需要报修，并说明具体怎么做>

范围性故障省略「数量：」这一行。
故障出在教室级设施上（总闸、交换机、投影、空调）时，
额外加一行【教室设施】。

## 严禁
- 严禁一次列出多个排查步骤
- 严禁输出大段解释和原理
- 严禁重复已经排除的检查项
- 严禁使用「首先、其次、最后」这种结构化列点
安全规则是被真实使用逼出来的。 早期版本把「教室总闸跳闸，合闸即可」列为可自修项， 于是 AI 会让学生反复推闸。而短路状态下反复合闸可能产生电弧、甚至引起火灾 —— 对每天都在机房里的学生管理员来说，这是不该出现的提示。

现在的约束是：总闸只允许推一次，推上去还跳就必须停手等电工。

4.2 如何约束 AI 的输出

除了提示词，还有三道工程约束：

手段 作用
max_tokens=300 物理限制回复长度，强制精简。写得长会被直接截断
temperature=0.3 降低随机性，让排查步骤稳定、专业，不出现发散内容
结构化标记 用 【诊断结束】【需要报修】【可自修】 三个标记，让程序能可靠地解析 AI 意图，而不必猜自然语言

标记解析与状态映射

def apply_markers(session, reply):
    """根据 AI 回复里的标记，更新会话状态"""
    if REPAIR_MARKER in reply:
        session.need_repair = True
    if SELF_FIX_MARKER in reply:
        session.self_fix = True
    if DONE_MARKER in reply:
        session.finished = True
        session.quantity = parse_quantity(reply)   # 从结论解析数量
    return reply


def parse_quantity(text):
    """容错解析：支持 "3 台" / "三台" / "十五台" """
    m = re.search(r'数量[:：]\s*(\d+)', text)
    if m:
        return max(int(m.group(1)), 1)
    # 中文数字、兜底匹配……
    return 1      # 解析不出时保守记为 1，绝不能是 0

4.3 提示词的迭代过程

提示词不是一次写对的，而是根据实际对话暴露的问题逐步补充规则：

发现的问题 补充的规则
用户说「电脑打不开」（模糊描述）时，AI 直接跳到排查电源开关 新增第 3 条：第一步永远是问清具体表现
用户答非所问时，AI 把上一个问题换个说法又问一遍 新增第 6 条：先确认信息，再用更简单的方式重问
AI 每次都问「指示灯亮吗？风扇转吗？」，像套模板 新增第 4 条：提问要多样化，按故障类型选择切入角度
用户已说明数量，AI 结论里仍写「数量：1 台」 新增第 8 条：数量要记住，不能写错，绝不能是 0
经验：提示词需要根据实际测试结果迭代。 第一版写出来的提示词往往不完善，必须通过真实对话发现问题、 再针对性补充规则。这条迭代记录已保存在 docs/开发过程记录.md 中。

只测不变的契约，不测易变的实现。 测「正常 + 损坏 = 设备总数」这条业务规则，而不是某个函数怎么写的—— 前者改代码时仍成立，后者稍作重构就误报。
要警惕「因为错误的原因而通过」的测试。 并发沉淀那条测试曾用 8 条只差一个字符的症状当「不同故障」， 而被测的去重逻辑会把它们判为重复：Windows 线程启动慢， 8 个线程在写入前都查完了重，于是全部写入、测试通过； Linux 上线程快，才露出真面目。

这种测试比没有测试更危险——它给虚假的安全感， 失败时表现为「时好时坏、只在某个平台挂」，很容易被加个重试糊过去。 判断很简单：结论取决于线程时序的测试，测的就不是业务规则。

5.3 典型缺陷与修复

以下是开发过程中真实发现并修复的典型缺陷，均有测试保护。

缺陷 1：异常被静默吞掉，知识库悄悄失效

现象：没有任何报错，程序运行正常，但知识库从未被成功加载。 

# 有问题的代码
try:
    with open(data_file, 'r', encoding='utf-8') as f:
        cases = json.load(f)['cases']
except Exception:
    return ""          # ← 所有异常被吞掉

# 调用方
if ctx:                # 空字符串判定为假 → 静默跳过知识库
    ...

根因：fault_cases.json 有两处逗号缺失导致 JSON 解析失败， 但异常被 except 吞掉并返回空字符串， 程序照常运行，表面上完全看不出问题。

修复：补全逗号；并加上实际验证——调用函数确认返回值非空。

经验：except 后返回空值是最危险的失败模式。 它把「配置坏了」伪装成「没有配置」。崩溃会立刻暴露问题， 而静默失败只会让功能「看起来能用、实际少了一块」。

缺陷 2：检索同义词缺口

现象：用户搜「整间教室断网」→ 无匹配。但知识库里明明有网络案例。

根因：断网 是关键词，但只对「用户说断网」加分； 案例正文写的是「无法上网」——这个加分永远加不上， 同义表达之间没有打通。

修复：新增同义词归一表，并在切分前扫描原文。

缺陷 3：下拉选项在深色主题下看不见

现象：下拉选项在深色主题下是白底浅字，几乎无法阅读。

根因：只给 <select> 控件设了深色样式， 没给下拉出来的 <option> 设。

修复：新增全局 select option 规则统一处理。

缺陷 4：文件初始化的「检查-写入」竞态

现象：CI 里 Ubuntu 两个 Python 版本时好时坏地失败， 而 Windows 始终通过。失败只用了 15~19 秒，像是并发用例挂掉。

根因：数据文件「不存在则创建」这一段的检查与写入之间没有锁， 而写入用的是 'w' 模式——它是截断写。 多线程同时首次调用时，后到的会把先到者刚写的内容清空。 

if not os.path.exists(RECORD_FILE):          # 多个线程都能通过
    with open(RECORD_FILE, 'w', ...) as f:   # 'w' 截断，覆盖先写入的
为什么本地一直没发现：这个竞态只在 Linux 上暴露，而且不是每次都触发—— 很容易被误判为「测试不稳定」而加个重试糊过去。实测 60 轮并发首次创建， 47 轮丢数据。成因与可重入改造见 3.5 节。

修复：整个检查-创建过程持锁；创建改用 'x' 模式 （并发进入者会拿到 FileExistsError，而不是把文件截断）。

验证：修复后 60 轮压测 0 失败；新增回归测试并确认 移除修复后该测试会立即失败，确保测试真正覆盖了这个缺陷。

七、AI 协作过程

7.1 协作方式

本项目全程使用 AI 辅助开发。协作方式不是「让 AI 写完整代码」， 而是人负责判断与验证，AI 负责实现与建议：

环节人的职责AI 的职责
需求分析 提出真实痛点，定义验收标准 给出数据结构与实现方案
编码实现 审查代码逻辑，要求逐段解释 生成代码，说明设计取舍
问题排查 提供完整报错信息与复现步骤 定位根因，给出修复方案
效果验证 实际运行验证，发现与预期不符之处 根据反馈调整

7.2 典型协作案例

案例：从「6 张表」到「1 张表」的需求纠偏

第一轮 Prompt（我）： 

设计导出功能：将报修记录导出成 excel。
表格顺序按照未报修-已报修-已解决处理，按照教学楼-教室进行分类。
要求体现教室历史故障原因和次数，并且反应现状：
目前教室有多少台能用，多少台不能用，不能用的一一对应好损坏时间和原因

AI 实现：生成了 6 个工作表（总览、故障总表、教室现状、损坏明细、故障统计、未录入台账）。 第二轮反馈（我）： 

导出的格式完全不行，你听我的要求，说完全部需求后再去做

第三轮（我给出完整需求）： 

用途需要领导看，要直观看出每间教室的情况。
你将工作表说明全部删除，表的最左侧是教学楼，
一次向下排，教学楼的右边接着对应的教室。
表头最上面是教学楼-教室-总设备数量-正常运行设备数量-损坏数量及其原因

进一步澄清（我）： 

因为是领导看，领导不管修没修，他只管现在能运行多少，
所以待修理和未报修都算作损坏，已解决不用单拎出来，
放入正常运作数量里。只留这一张。

最终结果：单张汇总表，一间教室一行， 「正常 + 损坏 = 设备总数」，账目可直接对上。

这个案例说明什么： AI 的实现能力很强，但它不掌握业务的真实约束—— 它不知道报表是给谁看的、领导关心什么。 第一版 6 张表在技术上没有错误，但解决的不是真问题。 把「用途、受众、判断标准」讲清楚，比反复描述格式更有效。

案例：AI 主动发现的隐藏缺陷

在实现「自动沉淀数据分离」时，AI 在回归测试中发现了一个更严重的问题： 

新沉淀一条"机房空调漏水导致地板大面积湿滑"
然后搜"空调漏水"  →  无匹配 ❌

刚存进去的案例，用关键词居然搜不到——等于沉淀了也没用。 根因是切分粒度不一致（查询是 4 字整段，案例被切成 3-gram）。

同一次测试还暴露出 AI 先前加的一个「降噪过滤器」是错的： 它只保留「能对应到已知词表」的词， 导致词表外的新领域（如"空调漏水"）永远无法沉淀。 该过滤器已被移除，改在打分环节解决假阳性。

AI 也会犯错，而且可能错得很隐蔽。 那个过滤器初衷是好的（挡掉跨词碎片噪音）， 但实现方式等于给知识库设了一道隐形准入限制。 凡是「让系统只能认识预先知道的东西」的设计， 都会在遇到真实世界的新情况时失效。 这个教训只有靠真实测试才能发现，靠阅读代码是看不出来的。
