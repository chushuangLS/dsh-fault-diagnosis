## 协作方式：人定方向，AI 落地

通读全部对话，有几个反复出现的模式：

**一、需求几乎全部来自真实值班场景。**
作者本人是学校机房主管，管 23 间教室、约 50 人的团队。「领导只看能运行多少台」「总闸掉闸别让学生反复推」这类判断，不是从产品方法论里推出来的，是从日常里长出来的。

**二、AI 的方向被否过很多次，而且每次都说清了为什么。**
**二、AI 的方向被否过很多次，而且每次都说清了为什么。**
「你的方向不对」「不是概念错了，是名称错了」
「这个分布没啥实际用，那个时段故障多能反映什么问题？」
「你听我的要求」—— 这些不是情绪表达，后面都跟着具体的理由和替代方案。

**三、先定设计再动手，避免返工。**
课表功能这一段最典型：用户两次叫停实现（「你先别做」「你先别生成，回复问题」），要求先把功能范围、界面布局、联动关系、判定口径全部拍完。结果后面一次实现就通过，没有再改结构。

**四、真实使用是最好的测试。**
10-16 到 10-17 的大部分改动，都来自用户实际用了一遍之后发现的毛病：状态名称不对、数量不刷新、拖拽不灵、提示词会误导学生去推闸。这些问题写测试是发现不了的。

## 附：这份记录本身也是产物

上面这些内容不是凭记忆补写的 —— 它们是从 DSH 的会话存档里解压、逐条抽取出来的原始输入。

抽取脚本已随仓库提供：`tools/extract_prompts.py`

```bash
# 看有哪些会话
python tools/extract_prompts.py --list

# 抽某一段时间的真实用户输入
python tools/extract_prompts.py --session session-xxxx --from 10-15 --to 10-17 --min-len 8
```

关键在于**只保留真人打的字**：

```python
if o.get("type") != "user/message":
    continue
# 系统注入的运行时上下文、技能清单、自动压缩摘要都带别的 source.kind，
# 混进来会污染记录 —— 它们不是人说的
if o["data"]["source"]["kind"] != "user":
    continue
```

会话文件本身不进仓库（含个人对话），只有筛选、脱敏后的这份记录公开。
