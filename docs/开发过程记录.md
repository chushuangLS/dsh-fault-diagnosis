## 一、项目起源

### 真实需求

本项目的需求直接来自作者的日常运维工作：

- 负责 **23 间机房教室、约 1840 台计算机设备**
- 管理 **50 人的学生运维团队**
- 每周值班 3-4 次，组织每周两次大扫除

在日常运维中发现的痛点：

1. **高频故障重复出现**：无法开机、网络中断、外设失灵等问题反复发生
2. **排查依赖个人经验**：新人上手慢，处理标准不统一
3. **经验无法沉淀**：老管理员离职后，经验随之流失

### 项目目标

把机房运维经验沉淀成**可检索、可复用的诊断工具**，降低对个人经验的依赖。

## 二、核心功能迭代记录

### 迭代 1：故障知识库（v0.1.0）

#### 需求描述（给 AI 的 Prompt）

> 我要做一个机房故障诊断工具。先用最简单的方案：
> 把故障案例存成 JSON 文件，包含现象、可能原因、排查步骤。
> 然后写个 Python 程序，用户输入关键词，程序匹配并输出对应案例。
> 请给出 JSON 的数据结构设计和最简实现。

#### AI 给出的方案

数据结构设计：

```json
{
  "id": "PC-001",
  "category": "开机故障",
  "symptom": "按开机键没有反应",
  "causes": ["电源线未插紧", "电源开关被关闭"],
  "steps": ["检查电源线两端是否插紧", "换一个插座测试"],
  "severity": "高",
  "est_time": "5-10 分钟"
}
```

程序结构：`load_cases()` 读文件 → `search_cases()` 匹配 → `show_case()` 输出

#### 落地结果

- 建立项目骨架（data / src / docs）
- 录入 2 条真实案例（开机故障、网络中断）
- 实现关键词匹配查询功能
- 对应提交：`2f004e8`、`b488b99`、`928f059`

#### 遇到的问题

**问题**：知识库只有 2 条案例，覆盖范围太小。

**分析**：这是起步阶段的正常状态，需要在实际使用中持续积累。

### 迭代 2：决策树逐步诊断（v0.2.0，暂缓）

#### 需求描述（给 AI 的 Prompt）

> 现在的问题是：输入故障现象后，程序只会输出一堆静态步骤。
> 我希望改成「逐步排查」：
> 比如开机没反应 → 先问「电源线插紧了吗」
> → 如果插紧了，再问「换个插座试试」
> → 如果还不行，再问「电源开关状态」
> 每一步根据用户回答走不同分支，最后给出确定的结论。
>
> 请设计这种「决策树」的数据结构，并实现问答流程。

#### AI 给出的方案

**数据结构设计**：节点 + 选项 + 跳转

```json
{
  "id": "PC-001-Q1",
  "question": "电源线插紧后按开机键有反应吗？",
  "options": [
    { "answer": "有反应了", "next": null, "conclusion": "电源线松动，已解决" },
    { "answer": "还是没反应", "next": "PC-001-Q2" }
  ]
}
```

关键设计：`next` 指向下一节点，`next: null` 表示诊断结束并输出 `conclusion`。

**代码实现**：`run_tree()` 用 `while` 循环，按用户选择不断跳转节点，直到 `next` 为 `null`。

#### 落地结果

- 设计了决策树数据结构
- 实现逐步问答流程（`decision_tree.py`）
- 录入「电脑无法开机」决策树（5 个节点）
- 对应提交：`0a57d0d`

#### 遇到的问题

**问题**：实际测试后发现，决策树的维护成本太高。

**分析**：
- 每增加一种故障，需要手工编写大量节点
- 分支是写死的，无法覆盖真实故障的多样性
- 用户输入仍然需要匹配触发词，本质上没有解决「描述难匹配」的问题

**决策**：**暂缓使用决策树**，代码保留备查，转向接入大模型 API。

### 迭代 3：接入大模型 API（v0.3.0）

#### 需求描述（给 AI 的 Prompt）

> 决策树方案先放一放。现在最大的问题是：
> 关键词搜索只能精确匹配，用户描述「电脑打不开」，
> 但知识库里写的是「开机没反应」，就匹配不上。
>
> 我想接入 AI 接口：
> 用户用自然语言描述故障，AI 给出专业的排查建议。
> 我手上有 DeepSeek 的 API Key。
> 请帮我实现，注意 Key 不能写死在代码里。

#### AI 给出的方案

**三个关键设计**：

1. **API Key 从环境变量读取**
   ```python
   api_key = os.environ.get("DEEPSEEK_API_KEY")
   ```
   —— 避免提交到公开仓库时泄露

2. **系统提示词约束输出格式**
   ```
   你是一名高校机房的资深运维工程师……
   要求：
   1. 先用一句话判断故障类别
   2. 列出可能原因（按可能性排序）
   3. 给出排查步骤，每步说明「做什么」和「看什么」
   4. 说明如何判断原因
   5. 给出处理建议（自己修 / 报修）
   ```

3. **把本地知识库作为上下文传给 AI**
   ```python
   messages.append({"role": "system", "content": context})
   ```
   —— 让 AI 的回答更贴合本校实际情况

#### 落地结果

- 新增 `ai_diagnosis.py` 模块
- 主程序改为「AI 优先，本地匹配降级」
- 对应提交：`f5b02ec`、`a6df58e`

#### 效果验证

**测试输入**：`老师电脑连投影仪没反应，屏幕黑的`

**AI 输出**（节选）：
```
故障类别：显示信号传输链路问题

先确认两个问题：
1. 老师电脑自己屏幕有画面吗？
2. 投影仪有没有亮灯/显示"无信号"？

排查步骤：
第 1 步：看投影仪画面
  - 显示"无信号" → 投影仪正常，是信号没进来，继续第 2 步
  - 完全黑 → 投影仪本身问题，跳到第 5 步

第 2 步：检查视频线两端
  - 插紧后画面出来 → 线松了，问题解决

第 3 步：切换投影仪信号源
第 4 步：切换电脑显示模式（Win+P）
第 5 步：换线/换设备交叉测试

处理建议：
- 1~4 步能解决 → 自己当场处理
- 换线换电脑都不行 → 报修
```

**关键意义**：知识库中**没有投影仪相关案例**，但 AI 依然给出了专业回答。
这验证了接入 AI 的核心价值：**突破了预设知识库的覆盖范围限制**。

### 迭代 4：改为对话式逐层排查（v0.4.0）

#### 需求描述（给 AI 的 Prompt）

> 我需要你改成层层递进的询问方式，不要一次性输出全部可能和步骤。
>
> 例：电脑打不开
> 问：具体是什么状态，你说详细
> 答：按电源没反应
> 问：先检查电源线是否接触不良，换根线试试
> 答：换了还是不行（这时候排除了电源线的问题，按此往后类推）
> ……最终输出结果，哪个地方的问题
>
> 现在程序最大问题是**过于重复冗杂，每次尽可能精简**。

#### 问题分析

v0.3.0 虽然接入了 AI，但实际使用体验很差：

- **一次性输出 5 个可能原因 + 5 个大步骤 + 每个步骤的子项**
- 内容长达上千字，用户在故障现场根本看不完
- 排查过程是「静态清单」，无法根据实际情况推进
- 无法体现「排除一个、进入下一个」的排查逻辑

#### AI 给出的方案

**核心问题**：程序每次只发一行就调用一次 API，AI 不记得上一轮说了什么。

**解决方案**：维护对话历史（`messages` 数组），每次把完整历史一起发送。

```python
class DiagnosisSession:
    def __init__(self):
        self.history = [{"role": "system", "content": SYSTEM_PROMPT}]

    def send(self, user_input):
        self.history.append({"role": "user", "content": user_input})
        response = self.client.chat.completions.create(
            model=MODEL,
            messages=self.history,      # 带上完整历史
            max_tokens=300,             # 限制长度，强制精简
        )
        reply = response.choices[0].message.content
        self.history.append({"role": "assistant", "content": reply})
        return reply
```

**提示词的关键约束**：

```
1. 每次回复只做一件事：要么问一个问题，要么给出结论
2. 第一步永远是问清具体表现 —— 用户说"电脑打不开"时，
   不要跳到排查，先问"按开机键后指示灯亮吗？风扇转吗？"
3. 绝不重复已经排除的检查项
4. 用户答非所问时，先确认他的信息，再把原问题用更简单的方式问一遍
5. 定位到原因时，第一行输出【诊断结束】，然后给结论
```

#### 落地结果

- 新增 `DiagnosisSession` 类，实现多轮追问
- 主程序改为对话循环，支持 `r` 重置会话
- 设置 `max_tokens=300` 强制精简回复
- 对应提交：`8ebf112`

#### 效果对比

**改进前**（一次性输出）：
```
故障类别判断：这是典型的"开机无反应"类故障……

可能原因（按可能性从高到低）：
1. 电源线松动或插座没电（最常见，占一半以上）
2. 机箱背后电源开关被关掉了
3. 电源供应器（PSU）损坏
4. 主板故障
5. 开机键本身坏了（较少见）

具体排查步骤
第 1 步：确认"没反应"的具体表现
  做什么：……
  看什么：……
  判断：……
第 2 步：检查电源线两端
  ……
（共 5 个大步骤，上千字）
```

**改进后**（逐层追问）：
```
[用户] 电脑打不开
[AI]   按开机键后，机箱指示灯亮吗？风扇转吗？

[用户] 按电源没反应，灯不亮
[AI]   检查一下机箱后面的电源线两头有没有插紧，插紧后再按开机键，有反应吗？

[用户] 换了电源线还是不行
[AI]   看一下机箱背面电源上的开关是不是被关到"O"那边了，拨到"I"再开机试试？

[用户] 开关是开的，灯也不亮
[AI]   把电脑插到旁边正常的机位上试试，能开机吗？
```

#### 遇到的问题

**问题**：第一版提示词下，AI 有两个毛病：

1. **用户说"电脑打不开"（模糊描述）时，直接跳到排查电源开关**，
   没有先问清具体状态
2. **用户答非所问时，AI 把上一个问题换个说法又问了一遍**

**原因**：提示词里没有规定「第一步要问清具体表现」，
也没有规定「用户答非所问时怎么处理」。

**修复**：在提示词中补充两条规则：

```
2. 第一步永远是问清具体表现……
6. 用户答非所问时：先简短确认他的信息，再把原来的问题问一遍（用更简单的方式）
```

**经验**：**提示词需要根据实际测试结果迭代**。
第一版写出来的提示词往往不完善，必须通过实际对话发现问题、再针对性补充规则。

### 迭代 5：Web 界面与流式输出（v0.5.0）

#### 需求描述（给 AI 的 Prompt）

> 比赛评分里有「用户体验与产品精细度」，而且方向说明强调前端。
> 现在的命令行版本没法录演示视频，需要做成网页版。
>
> 界面参考酒馆那种排版：每条消息带时间和抬头，用细线分隔，
> 不要气泡框。历史消息要累积在页面里，上滑能看，不刷新页面。
>
> 最重要的一点：AI 回复要**流式输出**，逐字出现，
> 并且**内容变多时自动平滑向下滚**。

#### 方案

**技术栈**：Flask（后端）+ 原生 HTML/CSS/JS（前端）+ ECharts（图表）

**分两步完成**：

**第一步：Web 化**
- `app.py`：Flask 后端，提供对话、记录、统计接口
- 复用原有 `ai_diagnosis.py` 和 `repair_log.py`，核心逻辑零改动
- 前端做成三页：诊断 / 报修记录 / 数据看板

**第二步：流式输出**
- 后端加 SSE 接口 `/api/chat/stream`
- `ai_diagnosis.py` 新增 `send_stream()` 生成器
- 前端用 `fetch` + `ReadableStream` 逐段接收

#### 落地的功能

| 功能 | 说明 |
|---|---|
| 落地页 | 三个功能入口卡片 + 动态背景 |
| 右侧抽屉 | 边缘把手拉出，显示会话状态与最近记录 |
| 数据看板 | ECharts 环形图 / 柱状图 / 折线图 |
| **流式输出** | 逐字出现 + 闪烁光标 + 思考动画 |
| **智能滚动** | 贴底时自动跟随；上滑看历史时不打断 |
| 消息排版 | 抬头（名字+时间）+ 正文，细线分隔 |

#### 遇到的问题

**问题 1：ECharts 的 CDN 不可达**

浏览器加载 `cdn.jsdelivr.net` 失败，图表空白。演示时风险很大。

**解决**：下载 ECharts 到 `web/static/`，改为本地引入。

**问题 2：SSE 生成器报 "Working outside of request context"**

流式接口首次测试直接失败。

**原因**：SSE 生成器在**请求上下文之外**执行，
而生成器内部调用了 `session.get('sid')` —— Flask 的 `session` 依赖请求上下文。

**解决**：把**所有 `request` / `session` 操作移到生成器之前**执行，
生成器内部只使用已经取出的普通变量。

```python
# 错误：在生成器内部访问 session
def generate():
    sid = session.get('sid')   # ← 报错

# 正确：先生成器外部取出
sid = session.get('sid')
def generate():
    ...  # 只用 sid 变量
```

**经验**：**流式/异步场景下，上下文对象不能跨边界使用**。
凡是依赖请求上下文的数据，必须在进入生成器前取出。

#### 效果

```
[用户] 501教室电脑开不了机

[机房运维助手]  2026-10-16 14:32
按开机键后，机箱指示灯亮吗？风扇转吗？
（逐字出现，带闪烁光标）
```

### 迭代 6：教室设备台账与报修闭环（v0.6.0）

#### 需求描述（给 AI 的 Prompt）

> 现在诊断能用，但台账是散的。我要把**教室和设备**也管起来：
>
> 1. 按「教学楼 → 教室」两级录入，每间教室记电脑总数和损坏数
> 2. 诊断时先选教学楼和教室，AI 就不要再问「哪间教室」了
> 3. 报修台账里也要带教学楼，方便按楼栋筛选
> 4. 新增 / 修改 / 删除教室都要能直接在页面上做
>
> 还有一点：AI 问教室号的时候，学生经常只回一个纯数字「501」，
> 之前识别不出来，要修掉。

#### 问题分析

v0.5.0 之后暴露出三个实际问题：

- **设备底数不清**：23 间教室、约 1840 台设备，损坏情况只在脑子里，没有台账
- **教室号识别不全**：`_extract_classroom()` 的正则要求「数字 + 教室」或「字母 + 数字」，
  用户单回一个纯数字 `501` 时匹配不到 —— 而这是最常见的回答方式
- **报修记录缺维度**：只记了教室号，没有教学楼，无法按楼栋统计

#### AI 给出的方案

**1. 新增 `classroom.py`，两级数据结构**

```json
{
  "buildings": [
    {
      "name": "教学楼A",
      "rooms": [
        { "name": "A101", "total": 60, "broken": 2, "note": "" }
      ]
    }
  ]
}
```

配套增删改查 + 汇总统计：

| 函数 | 作用 |
|---|---|
| `add_building` / `delete_building` | 教学楼增删（删楼连同其下教室） |
| `add_room` / `update_room` / `delete_room` | 教室增删改 |
| `summary()` | 教学楼数 / 教室数 / 总台数 / 损坏数 / 正常数 |
| `flat_rooms()` | 两级结构拍平，便于前端渲染下拉框 |

#### 遇到的问题

**问题：知识库静默失效**

排查过程中发现 `data/fault_cases.json` **无法解析**：

1. `NET-001` 的 `steps` 里有一行空的 `""`，且**后面漏了逗号**
2. `DISPLAY-001` 对象结束的 `}` 后面**漏了逗号**，直接跟了 `]`

**为什么一直没被发现**：`build_knowledge_context()` 用 `try/except` 包住了读取，
出错就 `return ""`（空字符串），而调用方只判断 `if ctx:` ——
**JSON 报错被完全吞掉，知识库一直以「空」的状态在运行**，
AI 表面上照常回答，所以从现象上完全看不出来。

```python
try:
    with open(data_file, 'r', encoding='utf-8') as f:
        cases = json.load(f)['cases']
except Exception:
    return ""          # ← 静默失败：坏了也不报错
```

**修复**：补全两处逗号，并实际验证函数返回值。

**经验**：
1. **JSON 编辑后必须运行验证**，这一条和「问题 1」是同一个坑，又踩了一次
2. **`except` 后返回空值是最危险的写法** —— 它把「配置错了」伪装成「没有配置」。
   至少应该打印一行警告，否则故障会被无限期隐藏

### 迭代 7：知识库检索增强与自动沉淀（v0.7.0）

#### 需求描述（给 AI 的 Prompt）

> 现在比赛评分里有「方法创新性 20%」，考察的是
> 「Prompt 工程精巧」「对 AI 智能体的驾驭能力」。
>
> 我现在的做法是：把知识库里所有案例都塞进提示词。
> 案例一多就浪费 token，而且无关案例会干扰判断。
>
> 能不能改成：先根据用户描述检索出最相关的几条，
> 只注入这几条？另外，每次诊断完的结论能不能自动
> 沉淀成新案例，让知识库越用越丰富？

#### 问题分析

**改造前的三个缺陷**：

| 缺陷 | 后果 |
|---|---|
| **全量注入** | 23 条案例全部塞进提示词，token 浪费严重 |
| **无检索能力** | 不管问什么，AI 都看到同样的案例 |
| **知识库靠手工维护** | 实际使用中没人愿意维护，永远是那几条 |

#### 方案

**分三部分实现**：

**① 检索（`knowledge.search`）**

不引入向量库（成本和复杂度都不划算），用**关键词加权匹配**：

```
对每个案例提取特征词
      ↓
与用户输入计算重合度
      ↓
按权重累加得分：
    分类命中  × 3.0   （故障大类一致，最可信）
    现象命中  × 2.0
    原因命中  × 1.0
    关键特征词 × 额外加成
      ↓
按得分排序，取 Top-3
```

**关键特征词表**：手工整理了 60+ 个故障特征词
（"蓝屏""花屏""断网""卡纸""话筒"等），命中即加权。

**② 注入（`build_context`）**

只把检索出的 Top-3 注入提示词，而不是全部。

**③ 沉淀（`save_case`）**

诊断完成后自动提取结构化信息入库。

#### 踩到的坑：分词产生的噪音匹配

**第一版**用 2-gram 滑窗切分中文，结果产生大量无意义碎片：

```
输入"机房空调旁边的电脑频繁自动关机"
切出：'的电'、'脑频'、'繁自'、'房空' ...
```

**后果**：这条查询**误匹配到了"网络故障"案例** ——
因为两边都有 `'的电'`（"整个教室**的电**脑" / "**的电**脑频繁"）。

**修复**：改成「关键特征词优先 + 长串 3-gram 且过滤虚词」策略。

**效果对比**：

| 版本 | 命中率 |
|---|---|
| 2-gram 滑窗（有噪音） | 误匹配严重 |
| 关键词优先（修复后） | **91%（21/23）** |

#### 沉淀策略上的两个设计取舍

**① 只沉淀"已验证"的结论**

需要报修的故障**不沉淀** —— 因为结论还没被验证是否正确。
把未验证的猜测写进知识库，会污染后续检索。

**② 去重阈值设得高**

第一版阈值设为 3.0，结果"空调导致自动关机"被判为
和"教室无法上网"重复，拒绝入库。**阈值提到 8.0 后正常。**

#### 效果

**知识库从 3 条扩充到 23 条**，覆盖 8 个分类：

| 分类 | 条数 |
|---|---|
| 系统故障 | 4 |
| 外设故障 | 4 |
| 开机 / 网络 / 显示故障 | 各 3 |
| 投影 / 打印 / 音频故障 | 各 2 |

**检索实测**（23 条测试用例）：

```
电脑开不了机，按电源没反应  → PC-001   ✅
整个教室都上不了网          → NET-001  ✅
电脑蓝屏了                 → SYS-001  ✅
鼠标不动了                 → DEV-001  ✅
打印机卡纸                 → PRT-002  ✅
...
命中率 91%（21/23）
```

**注入量对比**：

| | 改造前 | 改造后 |
|---|---|---|
| 注入案例数 | 23 条（全部） | **3 条（Top-3）** |
| 相关性 | 低（夹杂无关案例） | **高** |

#### 经验

1. **"全量注入"是 Prompt 工程的常见误区** ——
   信息不是越多越好，无关信息会稀释有效信息、干扰判断。

2. **不引入向量库也能做检索** ——
   在案例规模不大（几十条）时，关键词加权匹配的
   性价比远高于 embedding + 向量数据库。

3. **中文分词没有现成库时，宁可用关键词表，
   也不要用 n-gram 硬切** —— 噪音匹配比不匹配更糟糕，
   因为它会给出"看起来合理但实际错误"的结果。

## 三、遇到的典型问题与修复过程

### 问题 1：JSON 格式错误

**现象**：程序报错 `json.decoder.JSONDecodeError: Expecting ',' delimiter`

**原因**：手工编辑 JSON 时，在最后一条案例后多加了逗号。

**修复**：
```json
{
  "cases": [
    { "id": "A" },
    { "id": "B" },    ← 最后一条的逗号必须删掉
  ]
}
```

**经验**：JSON 对格式要求严格，编辑后必须运行程序验证。

> ⚠️ **同类问题后来又犯了一次**，见「[问题 4](#问题-4异常被静默吞掉知识库悄悄失效)」——
> 那次是**漏了逗号**（与本次相反），而且因为异常被 `except` 吞掉，
> 一直没有报错，属于更隐蔽的情况。

---

### 问题 2：API Key 泄露风险

**现象**：最初考虑把 Key 直接写在代码里。

**风险分析**：项目要求托管到公开仓库（Public），
Key 一旦提交，任何人都能看到并使用，可能造成费用损失。

**修复方案**：
1. 代码中从环境变量读取 Key
2. `.gitignore` 中排除 `.env` 等敏感文件
3. 提供环境变量配置说明，而非直接给 Key

```python
api_key = os.environ.get("DEEPSEEK_API_KEY")
if not api_key:
    raise ValueError("未找到 DEEPSEEK_API_KEY 环境变量...")
```

---

### 问题 3：决策树方案走不通

**现象**：决策树实现后，发现实际使用体验不佳。

**排查过程**：
1. 先按需求实现了完整的决策树引擎
2. 录入「开机故障」决策树进行测试
3. 测试发现：需要匹配触发词，用户描述方式仍然受限
4. 进一步分析：真实故障的多样性远超预设分支

**决策**：暂缓该方案，代码保留，转为接入 AI。

**经验**：**方案不是一次做对的**。先做出来验证，发现问题及时调整方向，
比一开始就追求完美方案更有效。

---

### 问题 4：异常被静默吞掉，知识库悄悄失效

**现象**：没有任何报错，程序运行正常，AI 也照常回答 ——
但 `data/fault_cases.json` 实际上**从未被成功加载**，知识库一直是空的。

**排查过程**：

1. 用 Python 直接解析知识库文件，确认语法错误：
   ```
   JSONDecodeError: Expecting ',' delimiter: line 39 column 9
   ```
2. 定位到两处：
   - `NET-001` 的 `steps` 中有一行空的 `""`，**后面漏了逗号**
   - `DISPLAY-001` 对象的 `}` 后面**漏了逗号**，直接跟了 `]`
3. 回头检查代码，找到「为什么没报错」：

   ```python
   try:
       with open(data_file, 'r', encoding='utf-8') as f:
           cases = json.load(f)['cases']
   except Exception:
       return ""          # ← 所有异常被吞掉
   ```

   调用方是 `if ctx:` —— 空字符串判定为假，于是**静默跳过知识库**，
   对话照常进行，表面看不出任何异常。

**修复**：
1. 补全两处缺失的逗号
2. 实际调用 `build_knowledge_context()` 验证返回值非空（3 条案例、177 字符）

**经验**：
- **`except` 后返回空值是最危险的失败模式**：它把「配置坏了」伪装成「没有配置」。
  至少应打印一行警告，或直接让异常抛出，否则故障可能隐藏很久
- **静默失败比崩溃更难发现**：崩溃会立刻暴露问题，
  而静默失败只会让功能「看起来能用、实际少了一块」
- 验证时不要只看「程序有没有报错」，
  要看**功能是否真的生效**（本例中应检查知识库内容是否进入了提示词）

好的提问（本项目实际使用）：

> 把故障案例存成 JSON 文件...

对于 AI 生成的代码，要求逐段解释，确保自己理解每一部分的作用。

**4. 保留完整的报错信息和排查过程**

遇到 bug 时，把完整报错发给 AI，而不是只说「报错了」——
这既是高效的调试方式，也留下了可复现的排查记录。
